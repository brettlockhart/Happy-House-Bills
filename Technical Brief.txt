# Technical Brief: Household Expense Tracker (v1)

## Project Overview

A web app for a couple to track shared household spending, split costs, and settle up. Two users per household. The core value proposition: **photo a receipt at the register → expense is logged before you're in the car.**

## Stack

| Layer | Technology |
|-------|-----------|
| Frontend | Nuxt 4 (Vue 3, Composition API, TypeScript) |
| Hosting | Cloudflare Workers (`nitro.preset: 'cloudflare-module'`) |
| Backend / DB | Convex (TypeScript, document store) |
| Auth / Multi-tenancy | Clerk (Organizations for multi-tenancy) |
| File Storage | Cloudflare R2 (via `@convex-dev/r2` component) |
| Transactional Email | Resend |
| OCR | Tesseract.js (client-side, v1) or Google Document AI (v1.1) |

**Key modules:**
- `@clerk/nuxt` — Clerk integration
- `@j-boardman/convex-nuxt` — Convex + Nuxt (supports `cloudflare-module` preset)
- `convex/react-clerk` — Clerk ↔ Convex auth bridge
- `@convex-dev/r2` — R2 file storage component

## Multi-Tenancy Model

- Each household = **one Clerk Organization** with exactly two members.
- Every Convex table has an `orgId: string` field (the Clerk Organization ID).
- Every query is scoped: `.withIndex('by_org', q => q.eq('orgId', orgId))`.
- `orgId` is derived from the active Clerk session on every request.
- Onboarding: User A signs up → creates organization → generates invite link → User B accepts via email (Resend) → both are members.
- A user belongs to exactly one organization (enforced in onboarding; no "switch household" UI in v1).

## Database Schema (Convex)

```typescript
// convex/schema.ts
import { defineSchema, defineTable } from "convex/server";
import { v } from "convex/values";

export default defineSchema({
  expenses: defineTable({
    orgId: v.string(),
    amount: v.number(),              // positive number, in dollars
    date: v.string(),                // ISO date string
    category: v.union(
      v.literal("groceries"),
      v.literal("utilities"),
      v.literal("other")
    ),
    paidBy: v.string(),              // Clerk user ID
    notes: v.optional(v.string()),
    // Receipt fields (nullable for manual entries)
    receiptImageId: v.optional(v.id("_storage")),
    receiptPHash: v.optional(v.string()),        // perceptual hash (dHash, 64-bit hex)
    receiptFingerprint: v.optional(v.string()),  // `${store}|${date}|${total}`
    // Status workflow
    status: v.union(
      v.literal("pending"),
      v.literal("approved"),
      v.literal("rejected")
    ),
    enteredBy: v.string(),           // Clerk user ID
    approvedBy: v.optional(v.string()), // Clerk user ID, set on confirm
    rejectReason: v.optional(v.string()),
    createdAt: v.string(),           // ISO timestamp
  })
  .index("by_org", ["orgId"])
  .index("by_org_date", ["orgId", "date"]),

  settlements: defineTable({
    orgId: v.string(),
    amount: v.number(),
    fromUser: v.string(),            // Clerk user ID
    toUser: v.string(),              // Clerk user ID
    date: v.string(),                // ISO date string
    createdAt: v.string(),
  })
  .index("by_org", ["orgId"]),

  // R2 component tables (auto-generated by @convex-dev/r2)
  // r2Files: { id, orgId, filename, contentType, size, ... }
});
```

**Derived balance (computed, never stored):**
```
balance = (sum of approved expenses paid by A) + (sum of settlements A→B)
        - (sum of approved expenses paid by B) - (sum of settlements B→A)
```
Positive = A owes B. Negative = B owes A.

## API Surface (Convex Functions)

### Mutations
| Function | Description |
|----------|-------------|
| `expenses:create` | Create a new expense (status: `pending`). Accepts optional receipt image. Computes and stores `receiptPHash` and `receiptFingerprint`. |
| `expenses:approve` | Set status to `approved`, set `approvedBy`. |
| `expenses:reject` | Set status to `rejected`, set `approvedBy` and `rejectReason`. |
| `settlements:create` | Record a settlement between the two members. |
| `orgs:create` | Create a Clerk Organization (called during onboarding). |

### Queries
| Function | Description |
|----------|-------------|
| `expenses:list` | Returns all expenses for the org, ordered by date desc. |
| `expenses:balance` | Returns the computed balance (who owes whom how much). |
| `expenses:pending` | Returns only pending expenses (for the confirmation UI). |
| `settlements:list` | Returns all settlements for the org. |

### Actions
| Function | Description |
|----------|-------------|
| `expenses:uploadReceipt` | Accepts an image file, uploads to R2 via `@convex-dev/r2`, returns the storage ID. Called before `expenses:create`. |

## Duplicate Detection

On `expenses:create`, before inserting:

1. **Image hash check:** Compute dHash of the uploaded receipt. Query `expenses` for same `orgId` + same `receiptPHash`. If found → return `{ duplicate: true, existingExpenseId }`. Frontend shows a warning.
2. **Fingerprint check:** Build `${store}|${date}|${total}`. Query for same `orgId` + same `receiptFingerprint` where `status != 'rejected'`. If found → same warning.
3. **Near-duplicate (manual entries only):** Same `orgId`, same `date`, `amount` within ±$0.01. Flag but don't block.

Do **not** use a unique DB constraint — the check is in application logic (Convex actions) so you can return a friendly response rather than a constraint violation.

## OCR Pipeline (v1)

**Client-side (Tesseract.js):**
1. User takes photo or uploads scanned image.
2. Tesseract.js runs in the browser (Web Worker). Extracts raw text.
3. Regex/heuristic parsing extracts: `store` (first line, uppercase), `date` (common date formats), `total` (line containing "TOTAL" or "$" at end of receipt).
4. Pre-fills the "Add Expense" form. User confirms/edits → submits.

**Fallback:** If OCR confidence is low or fields are empty, the form is blank and the user types manually.

**v1.1 (later):** Replace Tesseract.js with Google Document AI or Azure Form Recognizer for higher accuracy. The interface stays the same (image in → `{store, date, total}` out).

## UI Spec

**Single page, mobile-first. Three sections:**

### 1. Balance Header
- One large number: "$42.13 — Alex owes Sam"
- Updated in real-time via Convex subscription.

### 2. Action Buttons
- **"Add Expense"** → opens a modal:
  - Camera/upload button (triggers OCR if image)
  - Amount (pre-filled from OCR)
  - Date (pre-filled, defaults to today)
  - Category (groceries / utilities / other)
  - "I paid this" (defaults to current user)
  - Notes (optional)
  - Submit → creates `pending` expense → notifies other partner
- **"Settle Up"** → opens a modal:
  - Amount
  - "From" / "To" (auto-filled based on current balance direction, swappable)
  - Date (defaults to today)
  - Submit

### 3. Entry List
- Chronological list of expenses + settlements (interleaved, newest first).
- Each expense row shows: amount, store/category, who paid, status badge (pending ✓ / rejected ✗).
- Pending entries show a **Confirm / Reject** button to the other partner.
- Tap to expand: shows receipt image (if any), notes, who entered it.

**No other screens.** No settings, no dashboard, no reports, no history filter.

## Email Notifications (Resend)

Triggered from Convex mutations via `ctx.runQuery` + `fetch` to Resend API:

| Event | Recipient | Subject |
|-------|-----------|---------|
| Expense created (pending) | The other partner | "New expense: $84.32 at Loblaws — confirm?" |
| Expense approved | The person who entered it | "Confirmed ✓" |
| Expense rejected | The person who entered it | "Rejected: [reason]" |
| Settlement recorded | The other partner | "Settlement: $50.00 received" |
| Invite to household | Invitee | "Alex invited you to [Household Name]" |

Emails include a deep link to the relevant entry.

## Explicit Non-Goals (v1)

- No line-item extraction from receipts
- No categories beyond groceries / utilities / other
- No reports, charts, or analytics
- No CSV/bank statement import
- No multi-currency
- No push notifications (email only)
- No dispute workflow (reject + note is sufficient)
- No audit trail UI (data is in the DB, no "history" screen)
- No "switch household" or multiple orgs per user
- No native mobile app
- No settings screen
- No browser-native flatbed scanning (user scans to file, uploads)

## Acceptance Criteria

1. Two users can sign up, create a household, and invite each other.
2. Either user can add an expense manually (amount, date, category, who paid).
3. Either user can upload a receipt image → OCR pre-fills the form → submit.
4. The other user sees the pending expense and can approve or reject.
5. Only approved expenses count toward the balance.
6. Either user can record a settlement.
7. The balance updates in real-time for both users.
8. Duplicate receipt detection triggers a warning.
9. The app works on mobile browsers (iOS Safari, Android Chrome).
10. Total deploy time from clean repo to production: < 10 minutes.
